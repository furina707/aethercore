# AetherCore TUN 模式完整接管方案（纯 Python 数据面 + Fake-IP + IPv6）

## 问题根因
- `core/aether_tun.py` 从未被集成：launcher/core 均未导入它，其主循环只打印数据包，无 TCP 栈/UDP/代理桥接。
- launcher 在 `main()`（launcher.py:2193）中 `set_system_proxy(False)`，而状态栏谎称"纯 TUN 模式"（launcher.py:1501）→ 实际上只有手动配代理的应用流量进入内核。
- 只添加了 `198.18.0.0/15` 一条路由：无默认路由接管、无 DNS 劫持、无 IPv6。

## 目标架构
```
[所有应用流量 TCP/UDP/ICMP, v4+v6]
        ↓ 默认路由接管 (0.0.0.0/1+128.0.0.0/1, ::/1+8000::/1 → TUN)
[Wintun 网卡 198.18.0.1/15 + fd00:aether::1/64]  (aether_tun.py 扩展)
        ↓ core/tun_stack.py 分发器 (IPv4/IPv6 × TCP/UDP/DNS)
[TCP] core/tun_tcp.py 用户态 TCP 栈 → 每流转成 SOCKS5 CONNECT 到 127.0.0.1:7899
      (fake-IP → 域名 ATYP=domain；真实 IP → ATYP=IP) ← 域名/IP 分流规则全部复用
[UDP] UDP/53 → tun_dns.py Fake-IP DNS (A=198.18.x.x, AAAA=fd00:aether::x, 维护映射表)
      其余 UDP → 直连 NAT 中继 (socket 绑定物理网卡 IP, 按 IP 规则决策)
```
防回环：TUN 引擎 SOCKS5 连接走 loopback 不经过 TUN；内核 VLESS 出站 + DNS 上游查询**绑定物理网卡 IP**（`GetBestRoute/GetAdaptersAddresses` 自动探测物理接口与网关），并为节点服务器 IP 添加经原网关的 /32 主机路由双保险。

## 实施步骤

### 1. 基础设施（aether_tun.py 扩展）
- iphlpapi 封装补齐：IPv6 地址/路由（AF_INET6 SOCKADDR_INET）、`GetBestRoute`/`GetAdaptersAddresses` 探测物理网卡+网关、路由枚举（清理崩溃残留的 AetherCore 路由，启动时自动恢复）。
- `WintunDevice.configure_network()` 扩展：IPv6 地址 fd00:aether::1/64、MTU；新增 `install_capture_routes()`（v4 /1 ×2、v6 /1 ×2）与 `remove_capture_routes()`。

### 2. Fake-IP DNS（新文件 core/tun_dns.py）
- 劫持所有进入 TUN 的 UDP/53；A 记录返回 198.18.0.0/15 池、AAAA 返回 fd00:aether::/64 池（双向映射表，LRU 回收）；PTR 转发上游（绑定物理网卡 IP）。
- fake-IP 命中映射 → TCP 会话以域名 CONNECT，`decide_route` 的 proxy-domain/direct-domain 规则在 TUN 下继续生效。

### 3. 用户态 TCP 栈（新文件 core/tun_tcp.py，核心工作量）
- 每流状态机（SYN_RCVD→ESTABLISHED→FIN_WAIT/CLOSE_WAIT…），完整序号/ACK/窗口管理（含窗口缩放因子、MSS 1460）、基础重传与乱序容忍、RST/超时清理。
- ESTABLISHED 后起桥接线程：连接 127.0.0.1:7899 SOCKS5（域名或 IP），双向泵数据并切分成 MSS 段写回 TUN。

### 4. UDP NAT + 分发器（新文件 core/tun_stack.py）
- 读包循环：解析 IPv4/IPv6 头（含跳过 IPv6 扩展头）；TCP→tun_tcp，UDP/53→tun_dns，其余 UDP→NAT 流表（绑物理 IP 直连中继，空闲 TTL 清理）；ICMP 暂丢弃（文档注明限制）。
- IPv6 地址族全程对称支持。

### 5. launcher 集成
- 新配置指令 `tun on/off`（aether_gen.py 生成，默认 on）；launcher 启动/停止 TUN 引擎线程，失败（无 wintun.dll/非管理员）自动回退到系统代理模式；状态栏按实际模式显示；`shutdown_runtime` 中确保路由清理（try/finally + atexit）。
- 文档注明：TUN 模式下 `proxy-process` 进程规则失效（TUN 流无本地 socket 可归因），进程规则自动降级为按默认策略处理。

## 验证
- `route print` 确认 /1 路由与节点 /32 主机路由；退出后无残留。
- 浏览器全站、`curl`、Windows 更新等无代理配置应用全量走代理；DNS 泄漏测试（dnsleaktest.com）；IPv6（test-ipv6.com）；UDP 应用（如 NTP）；分流失效场景回归（direct-domain/proxy-domain/direct-ip）。

## 风险与限制
- Python 吞吐有限（预计几 MB/s～十几 MB/s），单核 GIL 瓶颈；已选纯 Python 方案属预期取舍。
- 无 SACK/PMTU 完整实现，极端弱网路径性能下降。
- UDP 走直连不代理（内核无 UDP ASSOCIATE/VLESS-UDP）；可选后续在内核补 UDP ASSOCIATE。
- ICMP 不转发，ping 域名将超时（TCP/UDP 不受影响）。
